# Scoped reads and explicit saves

A search result belongs to the query currently on screen. A save belongs to the submitted edit, even if the user keeps typing or leaves the page. Saba gives these operations different completion rules. Today `pageActions().request` combines scope and caller abort signals, and `api` parses the response. This decision adds ownership of results above those helpers. [Browser helpers](../../src/modules/dom.js) · [Component lifetimes](../SABA_UI_CONTEXT.md)

## Reads

A resource key is a snapshot of a flat tuple. The first element is a nonempty operation name string and the remaining elements are all normalized inputs affecting its result, for example `["item", "42"]` or `["itemSearch", "ada", "title", 1]`. The pilot accepts strings, booleans, null and safe integers, with −0 equal to 0. Compare type, value and position. Reject unsupported values and sparse tuples before starting a read. Two separately allocated equal tuples in the same authenticated session and tenant share one document cache entry, confirmed value and in-flight read. Changes to the caller’s original array leave that snapshot intact. The entry owns the transport controller. Each component owns its subscription.

Issuing or invalidating a read advances the entry’s generation. Success, failure and cleanup all check that the active partition still maps the key to the **same entry instance** and that its generation still matches. Delivery also checks that the subscriber’s scope is live and still attached. Switching keys detaches immediately. The last release removes the entry before aborting its transport. Reacquiring that key creates a fresh instance, even if its first generation again equals 1. These checks also apply when a transport ignores abort or decoding has already finished.

On first load, show pending. A key change displays only data for the newly selected key. During a same-key refresh, show its confirmed value with a refreshing indicator. A transient failure ends pending and exposes the error alongside that value. An authorized, definitive item deletion removes the confirmed record and disables Save. A dirty draft may be reviewed or copied. A 403 or opaque 404 clears the protected record and draft and retires affected list values. Session loss (401) or identity change releases the previous session/tenant partition, its journal and its editor state before the new identity can render. [Editor outcomes](0008-saba-routed-edit-forms.md)

For example, issue searches for `ad` and then `ada`. Deliver the `ada` response first and show Ada. Deliver the older response, or reject it and run its cleanup. The rows, error and loading indicator still describe `ada`. An independent component still watching `ad` may receive its own result.

## Saves

Submitting the editor at `/items/42` captures the item ID, `expectedRevision`, submitted fields and their local edit versions. The client allocates a fresh `operationId` for that logical save and serializes the PATCH body once. One save per editor and item may be outstanding. A repeated submit while pending shares it. The user can continue editing. Other editors may submit independently.

The Odin handler for `/api/items/42` authorizes the caller and atomically reserves a unique (tenant, caller, item, operation ID) with the original method, target and body bytes. Check this reservation before field validation or revision comparison. An identical duplicate sees pending or receives the recorded terminal status and body. A different submission under the same key receives HTTP 409 with `code: "operation_id_reused"` and leaves the original receipt intact. The client reports an operation identity error, preserves the unsent intention for review and cannot use that key’s receipt to acknowledge this submission. In one storage transaction the handler locks the pending reservation, rechecks write access and validates the snapshot. It records validation failures or updates the item only where its revision equals the submitted revision. The conditional update increments the revision on success. Zero matching revisions on an existing authorized item yields a revision conflict. The same transaction stores the terminal status and body. Two operations against one revision can produce at most one write.

| Server outcome | Live editor behavior |
| --- | --- |
| Success with canonical fields and new `revision` | Acknowledge the submitted operation. Apply canonical values to fields whose edit versions still match. Preserve later edits as dirty and keep any newer confirmed revision available for review. |
| HTTP 422 with `fieldErrors` mapping field names to strings | Keep the draft. A field error applies while the edit versions of all inputs used by its rule still match the submission. Use the entire submitted snapshot when the application has supplied no dependency set for the rule. |
| HTTP 409 revision conflict | Keep the draft and load the latest record for review. A subsequent save uses an explicitly reconciled draft and revision. |

The application registers every item search, sort and page in the `items` collection family. A confirmed save invalidates the exact detail key and every live entry in that family in its partition, including filters whose previous rows excluded the item. Advance their generations before publishing the mutation result and refresh live subscribers from committed state. An older read cannot restore old membership or revision. A late revision-8 receipt acknowledges its own operation after revision 9 has arrived. The shared detail keeps revision 9.

## Navigation and uncertain outcomes

Before dispatch, write one tab-session storage entry per (authenticated session, tenant, item, operation ID). In the pilot each top-level document owns its tab journal. Allocate IDs with a cryptographic random generator, claim a previously absent key before dispatch, and regenerate on a local collision. Never overwrite or remove another attempt’s entry. If writing fails, preserve the draft, report the failure and send zero requests. Two editors saving the same item create two entries. Disposal revokes permission to publish. The document tracks settlement for its active identity independently of any individual editor. On revisit or history restoration, verify identity, enumerate every outstanding entry for the item, check its receipt and refresh the record before admitting a new save. Remove each resolved entry independently. A restored editor uses receipt lookup only. The journal stores identifiers and carries no submitted fields or credentials.

For item 42 the pilot reads `GET /api/items/42/operations/{operationId}` with current authorization. A 401, 403 or opaque 404 follows the access-loss rules above and exposes no receipt data. A pending receipt (202) keeps the operation open. A terminal receipt (200) contains the recorded mutation status and body, including 422 or 409. A timeout or server failure leaves the journal intact for a later lookup. If the caller is authorized and the receipt is absent or expired, return 200 with `{"state":"unknown"}`. The outcome stays uncertain. Refresh the record and require explicit review before closing that entry and starting a new operation. Only an uninterrupted editor retaining its immutable submission may explicitly retry with the original ID and identical bytes inside the published retention window. Transport failure alone never resends a write.

## Recovery after a server restart

The application must persist the pending reservation and enough of the authorized submission to resume its work. Recovery scans pending reservations after restart and runs the same transaction as the original handler. Acquiring the lock and finding a terminal outcome completes recovery immediately. A crash before reservation leaves no operation. A crash after reservation leaves work to resume. A crash during the effect transaction rolls back both the record change and the terminal receipt. A crash after commit leaves both durable. Pending work stays recoverable until terminal.

The pilot uses a monotone, non-reused revision for each item identity across all its writes. Removal and recreation require a fresh identity or an unbroken revision history. The application publishes a minimum terminal receipt retention interval measured from completion. For a live retry the client measures that interval conservatively from its original dispatch. Recovery across tab close or cleared browser storage is outside the tab-session guarantee.

Exercise the pilot’s actual PATCH and receipt GET endpoints from the Odin suite run by `task test`, using persistent test storage.

- Pause after reservation. Send identical requests concurrently under one ID and inspect the pending receipt. Release the writer and verify one record change. Replay the original PATCH, then compare its terminal status and body with the receipt. Reuse the ID with changed bytes and verify the original receipt survives.
- Submit two IDs against one revision and assert one success and one stored revision conflict. Replay a stored 422 and a stored revision conflict after the record changes. Their status and body must match the original responses. Check that another caller or tenant cannot retrieve either receipt.
- Restart after reservation, during the effect transaction, and after commit but before reply. Reconcile against the same store and assert the final revision, write count and receipt together.

## Who finishes a save after an editor disappears

Once an operation is journaled and sent, the active document’s authenticated partition owns its transport outcome and receipt lookup. The editor owns only draft changes, messages and focus. Removing a keyed row releases its editor subscription. Its save can still invalidate a sibling’s list or update another live detail reader. Check partition identity before processing any completion, including access loss. An old 401 cannot clear a new login. Closing the whole document leaves reconciliation to the next verified document in the same tab.

For an indeterminate save with live affected readers, the partition checks its receipt even when the submitting editor is gone. Coalesce lookups per operation, use bounded backoff while active, and expose a pending or uncertain status with a read-only retry if the attempt budget is exhausted. A terminal success invalidates once for that operation. Refresh from a source that can see the committed write and reject detail values older than the highest confirmed revision. If another tab also has a live list, the pilot promises refresh on verified entry or return. Real-time cross-tab updates require an additional transport.

A lookup can overtake the original PATCH and return unknown before reservation. Treat that answer as uncertain, never as proof of failure or cancellation. Keep the original identifier available while reconciling. An explicit decision after reading the latest record may start a fresh operation against the reviewed revision. Its normal conditional update can still encounter the delayed original. Receipt replay is guaranteed within the published retention interval. A request arriving later still has to satisfy the non-reusable item revision precondition. Do not tell the user which operation succeeded unless a receipt establishes it.

The Odin route may classify a prepared request synchronously. Storage or a blocked receipt lookup must yield the connection owner through a nonblocking adapter or the bounded deferred-response path. Copy the payload and caller context needed by durable work before the request storage is released. The application owns recovery after reservation even if the client disconnects. Saturation before admission returns a retryable service error and creates no reservation. [Deferred response adapter](../../src/offload/response.odin)

- Remove the submitting row while another subscriber still watches a search the saved title will enter. Drop the response after commit. Require receipt reconciliation, correct membership in the surviving list, one server change and zero writes to the removed editor. Repeat while switching identity before the old receipt or 401 completes.
- Delay the first PATCH before reservation, return an unknown receipt, then admit the delayed request and an explicitly reviewed submission against the same base. Only one revision advances. Retire a terminal receipt, recreate an item and verify that the old revision can never mutate the new identity.
- Hold one storage operation at a barrier. A health request on a second HTTP/2 stream of the same connection must complete before it is released. Reuse the protocol-progress fixture’s single-owner barrier. ## Compatibility across deployments

The pilot versions its item, mutation, receipt and journal formats independently of the HTML build generation. Persist the accepted operation schema with its reservation. A newer server must finish pending operations and return their original terminal envelopes throughout the promised retention period. A new document must read older supported journal entries before enabling Save. An unrecognized journal entry stays intact and blocks that item’s Save until it can be reconciled. Do not include private fields in a migration.

Keep the original API compatible with an open editor during the supported deployment window. When an old client can no longer submit safely, identify its protocol version and return a typed `client_update_required` result **before reserving or writing a new operation**. Offer a native reload and a chance to copy unsaved edits while still authorized. Existing receipts remain readable by a supported client. Record revisions order changes to an item. They do not describe a build generation or an API format.

- Start a save with build A, publish B while its receipt is pending, then restore the editor in B using A’s journal entry. Verify one committed write, correct receipt decoding and deletion of only the matching pointer. Also exercise an obsolete client trying to submit a new operation, and an unknown journal version. Neither may silently write or discard the pending entry.

## Implemented adapters and verification

Create one read partition and one mutation partition for each active, verified session and tenant. The application supplies an opaque, non-secret session label, a transport and the resource family for each query. A mutation partition can publish to mounted reads with `onCommitted: (id, record) => reads.confirm(["item", id], record)`. The read partition accepts a `revisionOf` callback for monotone detail records. Collection revalidation can update a filtered view that previously excluded the item. [Read partition](../../src/modules/reads.js) · [Mutation partition and HTTP transport](../../src/modules/mutations.js)

The default item transport sends credentialed same-origin requests with `cache: "no-store"`. A journal entry carries an operation identifier and format version. A live editor may retry identical bytes explicitly when the application sets `retentionMs` to its server’s guaranteed minimum. A fresh document only checks receipts. If the outcome is unknown, it reads the current record and requires explicit review. The pilot uses tab-local session storage. Applications that need recovery across tab closure, cleared storage or devices supply a different persistence contract.

A receipt refresh moves the item between two still-mounted search views. Releasing both older, decoded search replies leaves the winning membership and detached editor untouched. A separate test pauses an actual reservation, publishes a new compiled page on the same origin, observes the receipt still pending after publication, and opens the new generation against the original operation. The recovered record advances one revision.
