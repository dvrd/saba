Saba · system architecture

From a socket to a live page.

Saba is one Odin process that speaks HTTP/1.1, HTTP/2 and HTTP/3, serves documents its compiler built ahead of time, and ships a small JavaScript runtime that attaches to them in the browser. This page explains how those parts fit together.

01 / The idea

The server never renders per request. The compiler decides what is HTML; the browser does the rest.

Two halves meet at the build generation. The server half moves bytes safely under budgets and deadlines. The UI half turns JSX into documents and modules before the first request arrives.

Who receives the bytes?

core

The HTTP server: TLS, HTTP/1.1, HTTP/2 and HTTP/3 on one non-blocking task runtime, with response coding, streaming, deferred responses, budgets, keep-alive and graceful drain.

Who decides what answers?

shared:saba + application

The facade most applications import. It prepares assets, modules and pages before listening, then routes each request through them in a fixed order before your handler.

What does the browser get?

jsx · pages · modules

The compiler emits markup it can prove as HTML and everything else as plain JavaScript modules, grouped into one immutable build generation.

What runs in the browser?

/__saba/*.js

A signal runtime with fine-grained bindings, an attach step for served documents, scoped reads, explicit saves, an editor and windowed lists. No hydration, no bundler.

What if the answer must wait?

offload · upstream

Adapters that return a deferred response: work on a thread pool, or a call to another HTTP server through Surf. The worker is free while they wait.

What if the connection changes protocol?

websocket

An HTTP/1 upgrade, or an extended CONNECT on HTTP/2 and HTTP/3, handed to the RFC 6455 codec. Development hot reload rides on it.

What about storage?

s3 · kakunou

S3 request signing with a non-blocking credential cache, and an optional SQLite handle that the facade passes to your handler.

How is it developed?

development

A supervisor rebuilds the program when sources change and swaps the child only after a successful build; the page reloads over a WebSocket.

02 / The map

How the packages connect

Read left to right. Your program configures the facade; the facade composes Saba's packages; those packages stand on shared libraries that krs installs from .krs/packages.json.

your code · server corefacadeUI buildadaptersshared libraries

The facade is optional. shared:saba/core runs alone with a proc(data, connection, request) -> Response handler; shared:saba/application adds preparation and routing without the database. The WebSocket codec is moving into shared:async/websocket; Saba switches once a tagged async and surf carry it.

03 / A request, end to end

Every protocol ends in the same handler

Listeners admit connections under a capacity and a budget. Each connection is one task on the executor. Whatever the protocol, a complete request reaches handle_request, which tries Saba's own routes in order before yours. The response then goes back out through the protocol that brought it.

  1. Admit

    The accept task takes a socket only while the server has capacity, opens a budget scope for the connection and registers a Connection_Task. A lost connection is skipped; an exhausted resource pauses accepting for a moment instead of spinning. HTTP/3 admits in its own connection table, with a per-address cap and Retry tokens once it is half full.

  2. Negotiate

    With TLS configured, the task runs the handshake first. ALPN picks h2 when the client offers it, otherwise http/1.1. An h2 connection becomes one session whose streams are tasks of their own.

  3. Receive

    Headers must arrive within the header timeout and fit 8 KiB. The body has a limit (4 KiB unless request_body_limit raises it per request) and a stall budget that each byte of progress re-arms.

  4. Route

    handle_request answers from development routes, built-in /__saba/ modules and build files, assets, modules or pages, unless the path is reserved for your handler. Everything else goes to your handler.

  5. Respond

    The response is coded with Brotli or gzip when the client accepts it and the body was not prepared already coded, then written in the framing of its protocol. On keep-alive the task returns to Idle.

04 / A connection's phases

One task, one state machine

A Connection_Task is resumed by whichever worker is free and runs until it would block, then yields. Its phase says where it is. A task never blocks a worker: waiting means returning Waiting and being woken by the reactor, a timer or a completed job.

05 / Kinds of response

A handler returns a value. What the value holds decides what happens next.

Handlers run on shared workers that are never preempted, so a handler must return quickly. Anything that waits is expressed in the returned Response.

06 / From JSX to a live page

The document is built once. The browser attaches to it.

Before the server listens, the compiler turns each page into HTML for every declared language plus the JavaScript that attaches to it. All of it is one build generation, named by a digest of its bytes. Every reader of a page in one language gets the same document; private data arrives later through authorized requests (ADR 0004).

What may become HTML?

Only what the compiler can prove

Intrinsic markup, static attributes and escaped text whose value and parsing context are known. Imported, recursive or parser-sensitive subtrees become browser-owned ranges. Nothing is executed during extraction.

What is a lowered row?

A direct DOM loop

A list row the compiler proves closed is written as plain DOM calls instead of signals. Where the loop could behave differently from the runtime, lowering is declined. URL attributes still pass through the runtime's checkedAttribute, so javascript: is refused either way.

Why one generation?

Old pages keep working

A document and its modules share an immutable URL prefix. A tab opened before a deploy keeps loading its own modules from the archive; an expired one fails to a readable page, never to newer bytes.

07 / Limits and deadlines

Every wait has a deadline and every byte has an owner

Memory is charged to budget scopes (operation, connection, global), so one request cannot starve the rest. Time is measured on a monotonic clock. Defaults below; all are configurable on Server.
